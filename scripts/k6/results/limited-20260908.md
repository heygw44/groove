# 한정반 구매 부하 재측정 (2026-09-08)

비관적 락 조회에서 `product` fetch join 을 뗀 변경의 회귀 확인용 측정이다. 1000 VU 가 재고 100 드롭을 동시에 구매하는 기존 시나리오(`scripts/k6/limited-purchase.js`)를 그대로 썼다.

## 이 측정이 답하는 질문과 답하지 못하는 질문

이 시나리오는 구매 트래픽만 돌린다. 상품 행을 건드리는 다른 트랜잭션(재고 조정, 상품 수정)이 없으므로, **락 범위를 줄인 효과 자체는 여기서 드러나지 않는다.** 그 효과는 `LimitedDropProductLockContentionIntegrationTest` 가 증명한다. 여기서 확인하려는 건 두 가지다. 초과 판매가 여전히 0건인가, 그리고 구매 경로가 느려지지 않았는가.

느려질 이유는 있었다. `@EntityGraph` 를 떼면 `OrderItem.of()` 가 상품 제목·가격을 읽는 시점에 프록시가 초기화되면서 SELECT 가 하나 늘고, 그 SELECT 는 드롭 행 락을 쥔 채로 나간다. 성공 요청 100건이 드롭 락에서 직렬화되는 구조라 임계 구간이 길어지면 꼬리 지연이 늘어난다.

## 프로토콜

두 모드 모두 컨테이너를 `--force-recreate` 로 새로 만들고(콜드), `VUS=50 STOCK=10` 으로 1회 워밍업한 뒤 본측정 1회. 같은 기계에서 연달아 돌렸다.

```bash
BACKEND_PORT=18080 docker compose --profile full up --build -d --force-recreate backend
BASE_URL=http://localhost:18080 VUS=50 STOCK=10 k6 run scripts/k6/limited-purchase.js   # 워밍업
BASE_URL=http://localhost:18080 k6 run scripts/k6/limited-purchase.js                   # 본측정
```

- before: `develop`(f5b7241)
- after: fetch join 제거본

## 읽기

- **초과 판매 0건 유지.** 재고 100에 성공 정확히 100건, `soldCount=100`. 이 변경이 이중 방어(드롭 행 `FOR UPDATE`, `(drop_id, member_id)` unique, `quantity >= 1` 조건부 UPDATE)를 건드리지 않았음을 확인했다.
- **느려질 것으로 봤던 꼬리 지연이 오히려 줄었다.** p95 1.94s → 1.25s. 쿼리가 한 건 늘었는데도 빨라진 이유는 확정하지 못했다. 락을 쥐는 쿼리가 두 테이블 조인에서 단일 테이블 조회로 바뀌면서 임계 구간에서 하는 일이 줄어든 것으로 보이지만, 1000 VU 가 같은 상품 행 하나를 함께 잠그던 상태가 사라진 영향과 구분하지 못했다. 추정이므로 그렇게 적어둔다.
- **두 모드 모두 p95 1초 임계값을 넘겼다.** 2026-09-04 측정(0.7~0.8s)보다 절대값이 높은데, 이번엔 같은 기계에서 Docker 빌드와 gradle 데몬이 함께 돌던 상태라 환경이 다르다. before/after 를 같은 조건에서 연달아 잰 비교는 유효하지만, 절대 수치를 이전 기록과 나란히 놓고 읽으면 안 된다.

## 곁다리로 고친 것

시나리오가 setup 단계에서 400(`COMMON_INVALID_INPUT`)으로 멈춰 있었다. 상품이 앨범에 속하도록 바뀐 뒤로 `newAlbum` 없이 상품을 만들 수 없는데 스크립트가 갱신되지 않았다. 카탈로그 작업 이후 이 시나리오를 한 번도 돌리지 않았다는 뜻이다.
