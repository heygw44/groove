# 한정반 선착순 구매 부하 테스트 결과 (2026-09-04)

`scripts/k6/limited-purchase.js` 로 1000 VU 가 재고 100 드롭을 동시에 구매하는 시나리오를 돌렸다. 판정 기준은 초과 판매 0건(NFR-02)과 `POST /limited-drops/{id}/purchase` p95 1초 이내다.

## 실행 환경

| 항목 | 값 |
|---|---|
| 머신 | Apple M4, 16GB, macOS. 앱·DB·Redis·k6 모두 같은 머신 |
| 앱 | `docker compose --profile full` 컨테이너. `-Xms256m -Xmx384m -XX:+UseSerialGC`, local 프로파일, show-sql·DEBUG OFF |
| DB / Redis | MySQL 8.0 / Redis 7 (Docker, OrbStack) |
| 커넥션 풀 | HikariCP 기본 10 (별도 진단 실행에서만 50) |
| Tomcat | 기본값(max-threads 200) |
| 부하 | k6 v2.0.0, `per-vu-iterations` 1000 VU × 1회, 오픈 시각 직후 일제 요청 |
| 데이터 | 실행마다 새 상품(초기 재고 100) + 드롭(총 100, 1인 1매) + 회원 1000명(setup 이 생성) |
| EC2 t3.micro | 미측정. 배포 뒤 같은 스크립트로 재측정 예정 |

프로토콜: 모드마다 컨테이너를 새로 만들고(콜드), 같은 규모로 1회 워밍업한 뒤 본측정 2회(A, B). 워밍업 없이 잰 첫 실행은 JIT 가 덜 풀려 p95 가 1.2~1.9초로 나왔고, 아래 표에는 별도로 적었다.

## 응답 코드 분포와 정합성 (전 실행 공통)

| 항목 | 값 |
|---|---|
| 요청 수 | 1000 |
| 201 (구매 성공) | 100 |
| 409 `LIMITED_SOLD_OUT` | 900 |
| 409 `LIMITED_ALREADY_PURCHASED` | 0 (회원당 1요청이라 나올 수 없음) |
| 그 외 코드 | 0 |
| `limited_purchase` 행 수 | 100 |
| `limited_drop.sold_count` / status | 100 / SOLD_OUT |
| `stock.quantity` | 0 |
| Redis `limited:stock:{id}` / `SCARD limited:buyers:{id}` | 0 / 100 (Redis OFF 모드는 키 없음) |
| **초과 판매** | **0건** (콜드·워밍업·본측정 15회 모두) |

## 응답 시간 (`http_req_duration{name:purchase}`, ms)

### Redis 선점 ON (기본)

| 실행 | min | p50 | p90 | p95 | p99 | max | 1000건 처리 시간 |
|---|---|---|---|---|---|---|---|
| 콜드(워밍업) | 353 | 1,170 | 1,360 | 1,390 | 1,440 | 1,490 | 1.6s |
| A | 72 | 681 | 773 | 802 | 880 | 928 | 1.0s |
| B | 122 | 526 | 627 | 675 | 1,000 | 1,000 | 1.2s |

### Redis 선점 OFF (`LIMITED_REDIS_ENABLED=false`, DB 행 락 + unique + 조건부 UPDATE 만)

| 실행 | min | p50 | p90 | p95 | p99 | max | 1000건 처리 시간 |
|---|---|---|---|---|---|---|---|
| 콜드(워밍업) | 124 | 1,020 | 1,160 | 1,220 | 1,290 | 1,300 | 1.4s |
| A | 44 | 707 | 796 | 833 | 885 | 921 | 1.0s |
| B | 51 | 603 | 699 | 718 | 759 | 765 | 0.8s |

### 진단: Redis ON + HikariCP 50

| 실행 | min | p50 | p90 | p95 | p99 | max | 1000건 처리 시간 |
|---|---|---|---|---|---|---|---|
| 콜드(워밍업) | 283 | 871 | 1,020 | 1,030 | 1,360 | 1,430 | 1.5s |
| A | 75 | 408 | 544 | 810 | 965 | 967 | 1.3s |
| B | 115 | 416 | 505 | 664 | 879 | 1,000 | 1.4s |

"1000건 처리 시간"은 k6 시나리오 시작부터 1000 VU 가 전부 응답을 받을 때까지의 벽시계 시간이다. 1000건이 1초 남짓에 끝나므로 순간 처리량은 약 800~1,000 req/s 다. k6 요약의 `http_reqs` 비율은 setup 의 회원 생성·로그인 3,010건까지 섞인 값이라 그대로 쓰지 않았다.

## 읽기

- 초과 판매는 어느 모드에서도 없었다. Redis 를 껐을 때도 0건인 것은 설계대로 DB 쪽 방어(드롭 행 `FOR UPDATE`, `(drop_id, member_id)` unique, `quantity >= 1` 조건부 UPDATE)가 최종 정합성을 혼자 지킨다는 뜻이다.
- 응답 시간은 ON 과 OFF 가 같은 수준이다. 이 규모(드롭 1개, 1000 요청, 같은 머신)에서는 실패 요청이 DB 행 락에 줄을 서도 락 점유가 짧아(상태 확인 후 즉시 예외) 지연이 크게 늘지 않는다. Redis 단계가 덜어 주는 것은 응답 시간이 아니라 DB 에 들어가는 트랜잭션 수다. 900건이 DB 트랜잭션에 들어가지 않는 차이는 DB 가 병목인 환경(t3.micro, 드롭 여러 개 동시 오픈)에서 드러날 것이므로 EC2 재측정 때 같이 본다.
- 꼬리 지연의 원인은 성공 요청 100건이 드롭 행 락에서 직렬화되는 시간이다. 성공 트랜잭션(구매 이력·주문·재고·이력 insert/update) 하나가 5~8ms 이고 100건이 순서대로 지나가므로 마지막 성공 요청은 0.6~0.9초를 기다린다. p95 가 이 근처에 붙는 이유다.
- Hikari 를 50 으로 늘리면 p50 은 600ms 대에서 400ms 대로 내려가지만 p95 는 그대로다. 실패 요청은 풀에서 커넥션을 얻는 대기가 줄어 빨라지고, 성공 요청의 직렬화 꼬리는 풀 크기와 무관하다.
- 개선 여지: 구매 진입 시 Redis 를 치기 전에 드롭을 DB 에서 한 번 읽는데(오픈/마감 시각 검증), 이 읽기가 실패 요청 900건에도 커넥션을 쓰게 한다. 드롭 일정을 캐시하거나 Redis 결과 뒤로 미루면 실패 경로가 DB 를 전혀 건드리지 않게 된다.

## 재현

```bash
docker compose --profile full up --build -d
VUS=1000 STOCK=100 k6 run scripts/k6/limited-purchase.js   # 워밍업
k6 run scripts/k6/limited-purchase.js                       # 본측정
LIMITED_REDIS_ENABLED=false docker compose --profile full up -d --force-recreate backend
k6 run scripts/k6/limited-purchase.js
```

호스트 8080 을 다른 프로세스가 쓰고 있으면 `BACKEND_PORT=18080` 으로 컨테이너 포트를 옮기고 `BASE_URL=http://localhost:18080` 을 준다. `docker compose up -d` 는 설정이 안 바뀌면 컨테이너를 재사용하므로 콜드 측정을 원하면 `--force-recreate` 를 붙인다.
