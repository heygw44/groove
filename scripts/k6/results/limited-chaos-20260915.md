# 한정반 카오스 장애 주입 측정 (2026-09-15)

정상 조건의 초과판매 0 은 `limited-purchase.js` 가 이미 증명했다. 이 측정은 러시 도중에 장애를 걸었을 때 선점 추적·대사(#398)·재고 키 재적재(#399)·서킷 폴백(#400)이 실제로 성립하는지를 본다. 같은 조건으로 수정 전 코드(develop bc87085, #398 직전)와 수정 후 코드(test/401 작업 트리)를 연속 측정해 무엇이 새고 무엇이 막혔는지를 나란히 놓는다.

## 프로토콜

- 시나리오: `scripts/k6/chaos/run.sh <scenario>` 로 실행. `limited-chaos.js` 가 회원 1,000명·재고 500 드롭을 만들고 150rps 로 20초 러시, 이어서 5rps 로 120초 테일을 보낸다. 러시 시작 T+2초에 러너가 장애를 주입한다.
- 케이스 4종. 이슈의 3종에 `REDIS_DOWN_SEC=10`(Redis 를 10초 정지) 한 종을 더했다. `docker compose restart redis` 는 0.4~0.7초 만에 끝나 서킷이 열릴 틈이 없어서, 폴백을 보려면 정지 시간을 늘려야 했다.
- 이미지: `groove-backend:before`(bc87085 워크트리에서 빌드), `groove-backend:latest`(작업 트리). `BACKEND_IMAGE` 로 바꿔 끼우고 `--force-recreate` 뒤 `VUS=50 STOCK=10 limited-purchase.js` 로 워밍업. 수정 후 세트는 케이스마다 워밍업을 한 번 더 넣었다(이유는 아래 "함정").
- 판정: k6 종료 후 70초(대사 30초 + grace 30초 + 여유) 기다렸다가 `verify-oversell.sh --local --chaos` 7항목, `analyze-chaos.mjs` 로 장애 전/중/후 구간 분포. 로컬 Apple M4, 컨테이너 백엔드(`-Xmx384m` SerialGC).

## 케이스별 상세

### redis-key-loss

| | 수정 전 | 수정 후 |
|---|---|---|
| 장애 전 / 중 / 후 요청 | 307 / 8 / 3,362 | 314 / 8 / 3,355 |
| `LIMITED_NOT_OPEN` | 3,358 (전체의 91.3%) | 0 (첫 측정에서는 2건 — 단일 비행 재적재 락에 밀린 요청) |
| 판매 | 319 / 500 | 500 / 500 |
| 대사 후 Redis | stock 키 없음, buyers 0 | stock 0, buyers 500 = DB |
| 복구 | 없음(138초 뒤 테스트 종료까지 400) | 마지막 400 → 정상까지 65ms |

수정 전은 `reserve` 가 `EXISTS stock == 0` 이면 `NOT_INITIALIZED` 를 돌려주고 끝이라 키가 사라지면 누구도 못 산다. 대사 스케줄러도 없어 자연 복구도 없다. 수정 후는 첫 `NOT_INITIALIZED` 에서 `rebuildOnce` 가 DB 기준으로 키를 다시 쓰고 같은 요청이 재시도해 성공한다. 백엔드 로그에 `한정반 Redis 재고 키 재적재` 가 정확히 한 번 남는다.

### redis-restart (짧은 재시작)

`docker compose restart redis` 는 로컬에서 0.4~0.7초다. 두 코드 모두 이 창에 걸린 요청은 한 자릿수라 결과 차이가 거의 없다. 수정 전 500 응답 1건(연결 끊김), 수정 후 0건.

수정 후 로그에 `대사 보정 stock 0→1 leaked=1` 이 한 번 찍혔다. AOF `appendfsync everysec` 라 재시작 직전 1초의 쓰기가 유실될 수 있는데, 이 경우 pending 에는 남았지만 DB 에 없는 선점 하나를 대사가 회수해 되팔았다. 수정 전 코드에는 pending 이 없으니 같은 유실이 나면 그 재고는 그대로 사라진다(이번 실행에서는 발생 안 함).

### redis-restart + 10초 정지 (`REDIS_DOWN_SEC=10`)

| | 수정 전 | 수정 후 |
|---|---|---|
| 정지 중 요청 | 1,413 | 1,595 |
| 정지 중 결과 | 500 ×1,389 (98.3%), 성공 24 | 503 ×1,264 (79.2%), 성공 63, ALREADY 268 |
| 정지 중 p50 / p95 | 1,005ms / 1,015ms | 3ms / 1,006ms |
| PONG 이후 오류 지속 | 500 ×600, 4.0초 | 503 ×492, 4.0초 |
| 오류가 끝난 시점(장애 시작 기준) | 14.8초 | 14.9초 |
| 완판 | 500 / 500 | 500 / 500 |
| 대사 후 Redis | 정합(정지 중 Redis 를 통과한 판매가 없어 어긋날 게 없음) | `155→106`, `106→0` 두 번 보정 후 정합 |

수정 전에는 Redis 명령이 1초 타임아웃(`spring.data.redis.timeout: 1s`)을 기다렸다가 500 이 된다. 정지 10초 동안 요청 1,413건이 전부 1초씩 매달렸고, 판매 24건은 Redis 가 완전히 멈추기 전 첫 초에 몰린 것이라 그 뒤로는 0 이다. 수정 후에는 연속 실패 5회에서 서킷이 열려 이후 요청은 3ms 만에 503 으로 거절되거나(대부분) DB 락 경로로 판매된다(permits 5).

여기서 세 가지가 눈에 띈다.

1. **폴백 판매가 초당 5건에 묶였다.** 타임라인에서 정지 중 매초 정확히 5건이 성공한다. permits 가 5 인 건 맞지만 DB 쓰기는 10ms 안팎이라 permits 만으로는 초당 수백 건이 나와야 한다. 원인은 커밋 뒤 pending 을 지우는 `LimitedPendingSynchronizer.clearAfterCommit → confirm()` 이 서킷 상태와 무관하게 Redis 를 부르고, Redis 가 죽어 있으니 요청 스레드가 1초 타임아웃을 그대로 먹는 것이다(성공 응답 p50 이 1,012ms). permit 하나가 1초씩 점유되니 5건/초가 상한이 된다. `recordAttempt` 는 서킷이 닫혀 있을 때만 부르도록 해 놓고 `confirm`/`release` 는 빠뜨렸다.
2. **PONG 뒤에도 4초간 503 이 이어진다.** Redis 가 응답해도 Lettuce 재연결이 3~4초 걸리고, 그 사이 HALF_OPEN 프로브가 한 번 실패해(`00:27:49 서킷 OPEN`) 다시 10초를 연다. 이 케이스에서는 그 10초 안에 드롭이 폴백 경로로 완판되어 서킷은 다음 요청(다음 케이스 워밍업)까지 HALF_OPEN 으로 남았다. 수정 전 코드도 같은 4초 동안 500 을 내므로 폴백 때문에 늘어난 시간은 아니다.
3. `서킷 OPEN` 로그가 1초 안에 130번 찍혔다. Redis 가 죽는 순간 `reserve()` 에 매달려 있던 요청들이 1초 뒤 한꺼번에 실패하면서 각자 `onFailure → open()` 을 부르기 때문이다. 상태는 이미 OPEN 이라 동작에는 영향이 없지만 `openedAt` 이 매번 갱신되고 로그가 쏟아진다.

### app-kill

| | 수정 전 | 수정 후 |
|---|---|---|
| 장애 창(kill → 헬스 UP) | 5.8초 | 5.7초 |
| 장애 중 결과 | 연결 오류 762 (98.2%) | 연결 오류 761 (99.2%) |
| 재기동 후 첫 정상 응답 | 70ms | 74ms |
| 누수(선점됐지만 커밋 안 됨) | 1건 | 5건 |
| 최종 | **DB 499 / Redis stock 0 / buyers 500.** 회원 1395 는 buyers 에만 있어 영원히 `ALREADY_PURCHASED` | 재기동 후 첫 대사(kill+35초, 기동 30초 뒤 첫 주기)가 `stock 0→5 leaked=5 cleared=1` 로 회수, 테일이 68초 시점에 5개를 마저 판매. **500 / 500** |
| verify | 4·5·6 FAIL(미달 1) | 7항목 PASS |

수정 전 누수는 첫 시도에서 바로 재현됐다. 150rps 러시에서 드롭 행 락 때문에 커밋이 초당 100건 안팎으로 직렬화되니 kill 순간 선점은 됐는데 커밋은 안 된 요청이 늘 있다(이번엔 1건, 수정 후 실행에선 5건). 수정 전 코드는 이 재고를 되찾을 길이 없고, 그 회원은 buyers 에 남아 다시 사지도 못한다. 수정 후는 pending 의 score 가 grace(30초)보다 오래된 항목을 대사가 "커밋되지 않은 선점"으로 판정해 stock 을 돌려주고 buyers 에서 뺀다. `cleared=1` 은 커밋은 됐는데 커밋 후 ZREM 직전에 죽은 한 건이다.

재기동 직후 250건 가까운 409 는 `LIMITED_SOLD_OUT` 이 아니라 `ALREADY_PURCHASED` 다(수정 후 1,060건). 회원 1,000명이 순환하는 시나리오라 이미 산 회원의 재시도인데, DB 가 SOLD_OUT 으로 바뀌기 전까지는 Redis 가 그렇게 답한다. 정상이다.

## 판정

- 초과판매: 8회 전부 0건. 이번 이슈가 묻는 "장애 조건에서도 NFR-02 가 성립하는가"는 그렇다.
- 대사 후 Redis·DB 불일치: 수정 후 4케이스 0건. 수정 전은 key-loss·app-kill 에서 영구 불일치.
- 장애 창의 실패 응답: key-loss 는 400 이 0~2건으로 줄었고, 10초 정지는 1초 걸리는 500 이 3ms 걸리는 503 으로 바뀌었다. app-kill 은 두 코드 모두 재기동까지 연결 오류라 차이가 없다(인스턴스가 하나라 당연하다).
- 복구 시간: key-loss 65ms, 짧은 재시작 0.2~0.4초, 10초 정지는 정지 종료 후 4초, app-kill 은 헬스 UP 후 74ms. 누수 재고가 되팔리기까지는 대사 주기 때문에 최대 60~80초.

## #400 폴백 채택 여부

**채택한다(`fallback-enabled: true` 유지).** 근거는 10초 정지 케이스다. 폴백이 없는 수정 전 코드는 정지 중 판매 0 에 사용자마다 1초씩 기다리게 했고, 폴백은 같은 시간에 63건을 팔면서 나머지를 3ms 만에 거절했다. 초과판매도, 대사 후 불일치도 없었다. "판매 중단 + 안내" 안은 사실상 수정 전 코드의 동작이고, 그쪽이 낫다고 볼 수치가 없다.

다만 폴백의 값어치를 깎는 결함 두 가지는 후속으로 고쳐야 한다(측정에서 드러난 순서대로).

1. 서킷이 CLOSED 가 아닐 때 `confirm()`/`release()` 를 건너뛴다. 지금은 폴백 판매 하나가 1초 타임아웃을 먹어 permits 5 로 초당 5건밖에 못 판다. 건너뛰면 DB 쓰기 속도(초당 수백 건)가 상한이 되고, 서킷 복귀 시 `resyncFallbackDrops` 와 대사가 어차피 Redis 를 DB 기준으로 다시 쓰므로 pending 을 안 지워도 정합에 문제가 없다.
2. `open()` 을 멱등으로 만든다. 이미 OPEN 이면 로그도 `openedAt` 갱신도 하지 않는다.

## #415 재측정 — 서킷 OPEN 중 커밋 후 Redis 호출 생략

위 "후속으로 고쳐야 한다" 두 가지를 fix/415 로 고치고 같은 조건(`REDIS_DOWN_SEC=10`, 150rps 러시, 회원 1,000·재고 500)으로 10초 정지 케이스만 다시 쟀다. 이미지는 `groove-backend:after-415`, 케이스 전에 워밍업 두 번(첫 번째는 앞 실행이 남긴 HALF_OPEN 을 닫는 용도).

| | #415 전(수정 후 세트) | #415 후 |
|---|---|---|
| 장애 창 | 10.8초 | 10.9초 |
| 정지 중 요청 | 1,595 | 1,607 |
| 정지 중 성공 | 63 (매초 정확히 5건) | **198** (+2s 4, +3s 111, +4s 51 → 완판) |
| 정지 중 503 `LIMITED_BUSY` | 1,264 | 425 (완판 뒤로는 409 `SOLD_OUT` 984) |
| 정지 중 p50 / p95 | 3ms / 1,006ms | 2ms / 1,006ms |
| 완판 시점(장애 시작 기준) | 정지 종료 뒤 +15초 | **+4초**(정지 중) |
| `서킷 OPEN` 로그 | 130회/1초 | **1회** |
| 완판 / 초과판매 | 500 / 0 | 500 / 0 |
| 대사 후 Redis | `155→106→0` 보정 후 정합 | `166→0` 보정 1회 후 정합, 7항목 PASS |

정지 중 성공 곡선이 permits 가 아니라 DB 쓰기 속도(드롭 행 락 직렬화, 초당 100건 안팎)에 묶인 게 보인다. +1s 의 216건 busy 는 서킷이 열리기 전(연속 실패 5회를 채우는 1초 타임아웃 구간)에 reserve 에 매달렸다가 폴백으로 몰린 요청들이고, 열린 뒤에는 폴백이 DB 속도로 팔아 +4s 에 재고가 끝났다. p95 가 여전히 1,006ms 인 건 이 초기 1초 구간 때문이고, 그 뒤 성공 응답은 수 ms 다(이전엔 성공 p50 이 1,012ms 였다).

pending 을 안 지워도 정합에 문제가 없다는 건 대사 로그 `166→0 buyersChanged=true` 한 줄로 확인된다. 정지 중 폴백으로 판 166건은 Redis 를 거치지 않았으니 지울 pending 자체가 없고, 서킷이 열리기 직전 reserve 까지 갔던 몇 건의 pending 은 grace(30초) 뒤 대사가 회수했다. 이후 pending 잔여 0, buyers = DB 구매자 집합.

첫 재측정은 같은 Docker 호스트에서 다른 작업(gradle 통합 테스트)이 돌아 장애 전 p50 이 414ms(평소 5ms)로 나와 버렸다. 카오스 측정은 호스트를 혼자 써야 한다는 걸 다시 확인하고 다시 쟀다. 원본: `scripts/k6/results/chaos-redis-restart-after-415-rerun-20260915-175301/`.

## 측정 환경 함정

- **서킷은 전역이고 HALF_OPEN 은 다음 요청까지 머문다.** 첫 수정 후 세트에서 app-kill 케이스의 첫 요청이 앞 케이스(10초 정지)가 남긴 HALF_OPEN 프로브가 되어 `서킷 CLOSED 복귀` 와 `대사 보정 499→498` 이 러시 시작 직후에 찍혔다. 결과 자체는 정합했지만 해석이 꼬이므로, 케이스 사이에 워밍업(`VUS=50 STOCK=10 limited-purchase.js`)을 한 번 돌려 서킷을 닫고 시작해야 한다. 드라이버가 그렇게 하도록 고치고 수정 후 세트를 다시 쟀다.
- **`ramping-arrival-rate` 는 `startRate` 를 안 주면 0 에서 램프업한다.** 첫 실행에서 T+2초에 요청이 3건뿐이었다. 장애가 "판매 도중"에 떨어지려면 `startRate: RATE` 가 필요하다.
- **`GROUP_CONCAT` 기본 상한 1,024자.** 구매자 약 200명부터 잘려 5번 항목(구매자 집합 비교)이 거짓 FAIL 이 났다. `group_concat_max_len` 을 세션에서 올렸다.
- **요청률은 커밋 속도보다 높아야 한다.** 드롭 행 락 때문에 커밋은 초당 100건 안팎이다. 150rps 로 올리고 나서야 app-kill 순간에 선점→커밋 사이 요청이 확실히 존재했다(60rps 첫 실행에서는 누수 0).
- **`--force-recreate` 는 컨테이너 로그를 지운다.** 첫 세트의 백엔드 로그가 이미지 교체로 사라져 재측정이 필요했다. 러너가 `backend-full.log` 를 남기도록 고쳤다.
- 이미 아는 것: 웜 JVM(재생성 뒤 워밍업 필수), 재고 < 회원 수(순환 회원이 잔여 재고를 사야 완판 여부를 볼 수 있다), 첫 구매로부터 10분 안에 판정(setup 40초 + 러시 141초 + 대기 70초 = 약 4분 20초), 테일이 90초보다 짧으면 대사가 되돌린 재고가 팔리기 전에 끝난다.
- 수정 전 코드에는 `limited:pending` 키 자체가 없어 3번 항목(pending 잔여 0)이 자동 PASS 다. 수정 전 결과는 4·5·6번으로 읽어야 한다.
- 로컬 docker 포트포워딩 때문에 앱이 죽어 있는 동안 새 연결이 refused 가 아니라 reset 으로 보일 수 있다. 분석기는 둘 다 `conn_error` 로 센다.
