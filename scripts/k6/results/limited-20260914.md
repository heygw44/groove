# 한정반 구매 부하 재측정 (2026-09-14)

선점 추적(`limited:pending:{dropId}` ZSET 기록)을 reserve/release Lua 에 얹은 변경의 회귀 확인용 측정이다. 1000 VU 가 재고 100 드롭을 동시에 구매하는 기존 시나리오(`scripts/k6/limited-purchase.js`)를 그대로 썼다.

## 이 측정이 답하는 질문

reserve 스크립트에 `ZADD` 한 줄, release 에 `ZREM` 한 줄이 늘었고 `write()` 커밋 뒤 `ZREM` 호출이 하나 붙었다. 구매 경로 왕복이 그만큼 느려졌는지, 초과 판매가 여전히 0건인지, 그리고 러시가 끝난 뒤 pending 키에 잔여 항목이 남지 않는지(커밋 후 ZREM 이 실제로 도는지)를 본다. 대사 스케줄러·서킷 폴백의 동작 자체는 통합 테스트가 증명하고, 장애 상황의 지연은 별도 카오스 측정 몫이다.

## 프로토콜

두 모드 모두 같은 Dockerfile 로 이미지를 따로 빌드해(`groove-backend:before` = develop bc87085 워크트리, `groove-backend:after` = 작업 트리) 같은 `docker run` 인자로 새로 띄우고(콜드), `VUS=50 STOCK=10` 으로 1회 워밍업한 뒤 본측정 1회. 같은 기계에서 연달아 돌렸고, 그동안 gradle·Docker 빌드는 돌지 않았다.

```bash
docker run -d --name groove-backend-k6 --network groove_default -p 18080:8080 -e SPRING_PROFILES_ACTIVE=local ... groove-backend:<tag>
BASE_URL=http://localhost:18080 VUS=50 STOCK=10 k6 run scripts/k6/limited-purchase.js   # 워밍업
BASE_URL=http://localhost:18080 k6 run scripts/k6/limited-purchase.js                   # 본측정
```

## 읽기

- **회귀 없음.** p95 1.03s → 1.00s 로 차이가 측정 오차 안이다. Lua 안에서 `ZADD` 하나가 늘어난 비용은 이 시나리오의 꼬리 지연(성공 100건의 드롭 행 락 직렬화)에 묻힌다.
- **초과 판매 0건 유지.** 이중 방어(드롭 행 `FOR UPDATE`, `(drop_id, member_id)` unique, 조건부 UPDATE)는 건드리지 않았다.
- **pending 잔여 0.** 성공 100건 전부 커밋 뒤 `ZREM` 이 돌았고, 실패 900건은 reserve 에서 걸러져 애초에 기록되지 않았다. 대사 스케줄러가 정상 운영에서 보정할 게 없다는 뜻이다(앱 로그에도 보정 로그 없음).
- 두 모드 모두 p95 가 1초 임계값 언저리다. 2026-09-08 측정(1.25s)보다 낮지만 그때는 빌드가 함께 돌던 상태라 절대값 비교는 의미가 없다. before/after 를 같은 조건에서 연달아 잰 비교만 유효하다.
