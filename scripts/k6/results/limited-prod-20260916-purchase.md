# 한정반 구매 운영 부하 재측정 — 구매 진입점 메타 캐시 적용 후 (2026-09-16, #431/#435)

`limited-prod-20260916-backlog.md`(#426 직후, 이하 "캐시 전")는 공백을 지나서도 201 이
한꺼번에 쏟아지지 않고 트리클링한다는 걸 확인했고, 원인을 `LimitedPurchaseService.purchase()`
가 Redis 선점보다 먼저 `findById(dropId)` 로 드롭 행을 읽는 순서로 지목했다(당첨자의 행 락
대기가 탈락자들의 DB 커넥션까지 잡아먹는 구조). #431은 이 조회를 `LimitedDropMetaCache`
로 옮겨 탈락자가 DB 를 아예 타지 않게 했다. 이 문서는 그 변경이 실제로 트리클링을
없앴는지, 그리고 그 자리에 새로 드러난 병목이 무엇인지를 정리한다.

## 이 측정이 답하는 질문 / 답하지 못하는 질문

답하는 것:
- 구매 진입점을 메타 캐시로 바꾼 뒤 409(SOLD_OUT)가 재고 소진 전에 즉시 나가는가.
- 탈락자가 정말 DB 커넥션을 쓰지 않는가(캐시 전/후 응답 분포 비교).
- 병목이 없어졌는가, 아니면 다른 자리로 옮겨갔는가.
- 초과 판매는 여전히 0인가.

답하지 못하는 것:
- 스왑(iowait)이 전혀 없을 때 당첨자 100명의 DB 쓰기가 몇 초에 끝나는지 — 이번 측정도
  #430 때와 같은 수준의 러시 스왑을 안고 진행됐다(§ 스왑 컨텍스트). 순수 캐시 효과만
  분리한 수치는 스왑을 없앤 뒤(#439)에나 나온다.
- Hikari `connection-timeout`(30s)·풀 크기(10)를 지금 당장 조정해야 하는지 — 스왑이 남아
  있는 상태에서 이 값을 만지면 어느 쪽 효과인지 분간이 안 된다.
- 1000 VU 미달 판매 2건이 "메타 캐시가 stale 상태를 오래 들고 있어서"가 아니라 "Hikari
  타임아웃으로 write() 자체가 완주 못 해서"라는 건 로그로 확인했지만, 메타 캐시 TTL(3초)이
  이 실패에 조금이라도 기여했는지는 별도로 분리하지 않았다.

## 읽기

확정한 것:
- **#431의 목표는 달성했다.** 1000 VU 기준 409가 재고 소진 전 첫 응답 초부터 201과 동시에
  나간다 — 캐시 전엔 201이 다 끝난 뒤에야 409가 시작됐다. 탈락자가 더는 DB 커넥션 줄에
  서지 않는다.
- **병목이 사라진 게 아니라 옮겨갔다.** 캐시 전엔 탈락자 900명이 `findById`로 당첨자
  유입 속도를 자연 조절해(초당 5~22건) Hikari 타임아웃까지 안 갔다. 이번엔 당첨 100명이
  거의 동시에 `write()`에 도달해 커넥션 10개에 90명이 줄을 섰고, 그중 99명이 30초
  타임아웃을 넘겨 504로 실패했다.
- 초과 판매는 두 단계 모두 0건(대사 이후 기준). 실패율이 늘어난 상황에서도 이중 방어
  (Redis 선점 + DB 조건부 UPDATE)는 재고 상한을 넘기지 않았다 — 다만 1000 VU는 상한
  미만(98/100 즉시, 대사 후 100/100)으로 끝나는 새로운 실패 양상이 나왔다.
- 2000 VU 503 1170건은 캐시와 무관한 별개 원인(Redis 서킷 OPEN, iowait로 인한 Redis
  1초 타임아웃 연속)이다 — 앱 결함이 아니라 인프라 지연이 서킷을 열었다.
- `/actuator/metrics`가 이번엔 열려 있어(#436) heap이 병목이 아니라는 걸 처음으로 직접
  확인했다 — committed 237MB가 `-Xmx384m` 안에서 여유 있게 유지됐다.

추정인 것:
- 스왑이 전혀 없었다면 당첨자 100명의 DB 쓰기가 5~7초 안에 끝나 30초 타임아웃을 넘기지
  않았을 것이라는 판단은 이번 측정만으로 확증하지 못한다 — 스왑을 없앤 뒤(#439) 같은
  시나리오를 다시 돌려야 분리된다.
- 1000 VU 러시에서 CPU가 100%를 넘는 순간과 iowait 피크가 시간상 어긋나 있어(iowait는
  러시가 끝난 뒤 더 높다), 504의 직접 원인이 iowait 자체인지 CPU 포화인지 완전히
  갈라내지 못했다.

- 1000 VU는 배포 5분 뒤 콜드 JVM, 2000 VU는 직전 러시의 스왑을 안고 시작하는 웜 — 두
  단계 모두 "정상 상태"의 성능은 아닐 수 있다.
- 이번 측정은 캐시 도입 효과(탈락자 응답 즉시성)와 그 결과로 드러난 새 병목(당첨자
  커넥션 경합)을 함께 봤을 뿐, 두 효과를 스왑 없는 환경에서 따로 떼어 보지 않았다.
- VU는 2000까지만 확인했다.

## 후속

- #439 — 인스턴스 업그레이드 여부를 판단한 뒤, 스왑 없는 환경에서 이번 시나리오를

  검토한다 — 지금 만지면 스왑 효과와 섞여 어느 쪽 개선인지 분간이 안 된다.
- 2000 VU 서킷 OPEN·DB 폴백 503 1170건은 #431 범위 밖이다. Redis 응답 지연이 iowait에
  기인하므로 이것도 #439 재측정에서 같이 관찰한다.

## 재현

VPN이 켜져 있으면 반드시 끈다.

```bash
MAX_MEMBERS=4000 scripts/k6/prod-run.sh --smoke                          # VU 10 / 재고 3 으로 한 바퀴 확인
MAX_MEMBERS=4000 scripts/k6/prod-run.sh --vus "1000 2000" --stock 100    # 본측정
scripts/k6/cleanup-prod-loadtest.sh --drop-ids "21,22"                   # dry-run
scripts/k6/cleanup-prod-loadtest.sh --drop-ids "21,22" --apply
```

체크리스트는 직전 문서와 같다 — VPN 해제 확인, `MAX_MEMBERS`를 회원 총량보다 크게, 배포
워크플로와 겹치지 않는 시간대. macOS `awk`엔 `strftime`이 없어 타임스탬프 변환은
`date -r <epoch초>`를 쓴다(초 단위이므로 밀리초 값은 1000으로 나눈 정수부를 넘긴다).

`vu-1000/`·`vu-2000/` 안의 `k6-stdout.log`·`verify.txt`·`pre-check.txt`·`post-check.txt`·
`resources.csv`, `jvm-metrics.log`, `snapshot-before/after.txt`, `baseline-before/after.txt`
로 역추적된다(결과 디렉토리는 gitignore 대상이라 로컬에만 있다).
